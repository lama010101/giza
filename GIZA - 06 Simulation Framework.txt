# 1. Simulation Framework

This chapter defines the simulation subsystem. It is one of the most critical architectural components because it separates **physical simulation** from **archaeological interpretation**.

A simulation demonstrates **what would happen if a set of assumptions were true**. It does **not** establish that those assumptions are historically correct.

This distinction must remain explicit throughout the application.

---

# 1.1 Design Philosophy

The simulation engine answers questions such as:

* Could water have flowed through this conduit?
* How would a chamber resonate at a given frequency?
* What pressure would develop under these conditions?
* How would sediment accumulate?
* How would sound propagate through connected cavities?

It does **not** answer:

* Why the builders created the structure.
* Whether a specific theory is historically correct.

---

# 1.5 Parameter Sets

Every simulation stores its complete configuration.

Example:

```json
{
  "simulation":"Hydraulic",
  "waterLevel":18.4,
  "flowRate":0.7,
  "temperature":22,
  "viscosity":"fresh_water",
  "gravity":9.81
}
```

Parameter sets are versioned and shareable.

---

# 1.6 Parameter Provenance

Every parameter is classified.

| Source       | Example               |
| ------------ | --------------------- |
| Measured     | Chamber dimensions    |
| Published    | Limestone density     |
| Estimated    | Roughness coefficient |
| User-defined | Water level           |
| Experimental | Resonance damping     |

Users always know which parameters originate from measurements and which are assumptions.

# 1.7 Hydraulic Simulation

The hydraulic engine models:

* Standing water
* Gravity flow
* Pressure
* Filling
* Emptying
* Surface elevation
* Water velocity
* Turbulence (simplified)
* Conduit connectivity

The MVP assumes incompressible Newtonian fluid behavior.

---

Required inputs include:

```text
Geometry

Water Sources

Water Level

Material Roughness

Gravity

Flow Restrictions

Boundary Conditions
```

All inputs are editable in Research Mode.

The engine computes:

* Flow direction
* Pressure field
* Velocity vectors
* Fill time
* Drain time
* Water volume
* Estimated energy loss

Outputs are timestamped and exportable.

# 1.10 Hydraulic Visualization

# 1.11 Hydraulic Validation

Simulation results are compared against:

# 1.16 Geological Simulation

Phase 2 introduces geological analysis.

Capabilities include:

* Stratigraphic visualization
* Rock property assignment
* Fracture mapping

# 1.17 Structural Simulation

Future structural analysis may evaluate:

* Load distribution
* Stress
* Compression
* Potential failure zones
* Deformation

This module should integrate with established finite-element software where practical rather than reimplementing advanced solvers.

---

# 1.18 Simulation Independence

A single geometry supports multiple simulations.

Example:

```text
Level 3

├── Hydraulic
├── Acoustic
├── Geological
└── Structural
```

No simulation modifies the underlying archaeological model.

---

# 1.19 Time Control

Simulations support:

* Pause
* Resume
* Step forward
* Step backward (replay)
* Variable speed

Replay is based on recorded states rather than reversing the solver.

---

# 1.22 Scientific Transparency

Example:

```text
Simulation results illustrate the behavior of the selected model under the specified assumptions. They do not constitute evidence that the historical system operated in this manner.
```

# 1.25 Performance Strategy

The engine supports progressive complexity.

| Mode     | Description                  |
| -------- | ---------------------------- |
| Preview  | Instant approximate solution |
| Standard | Interactive accuracy         |
| Research | Higher fidelity, slower      |
| Offline  | Maximum precision            |

# 1.26 Validation Framework

Each simulation includes objective validation metrics.

For example:

**Hydraulic**

* Conservation of mass
* Boundary condition verification
* Numerical stability

**Acoustic**

* Energy conservation
* Mesh resolution adequacy
* Frequency convergence

Validation results appear before the simulation is accepted.

# 1.27 Proposed Enhancement: Evidence-Aware Simulations

A distinctive feature for GIZA is to make simulations aware of evidence confidence.

Instead of treating all geometry equally, each simulation element carries uncertainty.

Example:

```text
North Conduit

Geometry Confidence: 84%

↓

Simulation Confidence Limited To 84%
```

Areas reconstructed with lower certainty produce wider confidence intervals in simulation outputs.

This avoids presenting highly precise numerical results derived from uncertain geometry.

---

# 1.28 Proposed Enhancement: Multi-Scenario Simulation Matrix

Rather than running one scenario at a time, researchers can define parameter ranges.

Example:

| Water Level | Roughness |           Result |
| ----------- | --------: | ---------------: |
| 17.0 m      |       Low |           Stable |
| 17.0 m      |      High |        Slow Flow |
| 18.5 m      |       Low |         Overflow |
| 18.5 m      |      High | Partial Overflow |

The application can then visualize sensitivity analyses instead of isolated simulations.

This is valuable because archaeological hypotheses often depend more on parameter uncertainty than on the solver itself.

---

# 1.29 Proposed Enhancement: Coupled Simulations

Long-term architecture should permit modules to interact.

Example:

```text

↓

```

or

```text

↓

↓

↓

```

This enables interdisciplinary exploration while preserving modularity.
